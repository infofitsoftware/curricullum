# Chapter 2: Defining the Problem

## Learning Objectives

After this chapter you should be able to:

1. Write a clear problem statement for your product.
2. Convert user needs into simple user stories.
3. Check whether a story is testable and user-centered.
4. Discuss and improve weak statements in class.

---

## 1. Why This Matters

If the problem is fuzzy, features become random.

Developers need a shared sentence like:

> “We are solving X for Y so that Z.”

That sentence guides design, coding, AI prompts, and testing later.

---

## 2. Core Concepts

### Problem statement

**Definition:** A short description of who has what problem, in what context, and why it matters.

**Useful template:**

> **[User]** needs a way to **[goal]** because **[pain/context]**.  
> Current workaround **[workaround]** fails when **[failure point]**.

**Example:**

> Club members need a way to register for campus events because WhatsApp forms get lost.  
> Current workaround (forwarded Google forms) fails when links are buried and admins cannot see a clean list.

### User story

**Definition:** A simple requirement from the user’s point of view.

**Template:**

> As a **[user]**, I want **[action]**, so that **[benefit]**.

**Examples:**

* As a club member, I want to register for an event, so that I can secure my seat.  
* As an admin, I want to view the registration list, so that I know who is coming.

---

## 3. Interactive Class Flow

### Talk (5 min)
Teacher shows 3 problem statements on board: one vague, one too broad, one good.  
Students vote which is usable.

### Activity A (15 min) — Write your problem statement
Students draft using the template for their Module 2 product.

**Peer review pairs (10 min):**  
Partner marks:

* Is the user clear?  
* Is the pain real?  
* Is the workaround named?  

Revise once.

### Activity B (20 min) — Story wall
Each student writes **4 user stories** on notes/board.

Class rule: every story must have user + want + so that.

**Teacher filter live:**

* “As a user I want a modern UI…” → weak (not outcome-linked)  
* “As a member I want confirmation after registration…” → stronger  

### Activity C (10 min) — Acceptance hint
For 1 story, add 2 checks:

> This story is done when:  
> 1) …  
> 2) …

(No need for formal QA language yet.)

---

## 4. Common Mistakes

1. Problem statement that only says “people need an app.”  
2. Stories written as tasks for developers (“As a developer I want React…”).  
3. One giant story that hides 10 features.  
4. Copying stories from AI with no link to your interviews.

---

## 5. AI Use (light)

Use AI to improve clarity, not invent users.

**Better prompt:**  
> “Improve this problem statement for clarity. Keep my facts. Make it under 60 words: …”

---

## 6. Exit Ticket

1. Final problem statement  
2. Four user stories  
3. One story with “done when” checks
