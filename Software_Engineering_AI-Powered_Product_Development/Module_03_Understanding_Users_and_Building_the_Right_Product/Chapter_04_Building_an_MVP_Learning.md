# Chapter 4: Building an MVP

## Learning Objectives

After this chapter you should be able to:

1. Define MVP in plain language.
2. Describe your product’s MVP in one page.
3. Explain what you will learn from the MVP.
4. Avoid fake MVPs that are either too big or useless.

---

## 1. Why This Matters

**MVP** is one of the most used words in product and startup conversations.

Used badly, it means “half-broken app.”  
Used well, it means “smallest useful version that helps us learn.”

As developers, MVP protects you from endless building before feedback.

---

## 2. Core Concepts

### MVP (Minimum Viable Product)

**Definition:** The smallest version of a product that delivers enough value to real users and gives the team feedback for what to improve next.

Break it down:

* **Minimum** — as small as possible  
* **Viable** — still useful enough  
* **Product** — something users can try (not only a slide deck forever)

### What MVP is not

* a perfect polished final release;
* a random prototype with no core job;
* “all features, low quality.”

### MVP learning question

> After someone uses this, what will we know that we do not know today?

Examples:

* Will students actually register on a link?  
* Can admins manage the list without WhatsApp?  
* Is due-date tracking enough, or do people also need reminders immediately?

## 3. Interactive Class Flow

### Concept check (5 min)
Teacher asks: “Is a logo an MVP?” Students respond.  
Correct direction: No — users cannot complete a job with only a logo.

### Activity A (15 min) — MVP one-pager
Fill for your product:

```text
Product name:
Primary user:
Core job:
Must-have features (max 5):
Out of scope:
How someone will try it this month:
What we will learn from first users:
```

### Activity B (15 min) — Hot seat
3–4 students present MVP one-pager in 60 seconds.  
Class asks only:

1. “What is the core job?”  
2. “What did you cut?”  
3. “How will you get one real user to try it?”

### Activity C (10 min) — Link to future modules
Teacher maps:

* MVP screens → later HTML/CSS  
* Forms/lists → later JS/backend/DB  
* Feedback → later improvement module  

Students see why today’s MVP decision matters for months.

## 4. Relatable MVP Examples

| Idea | Good MVP | Too big for now |
|------|----------|-----------------|
| Salon booking | Request slot + owner list | Payments + staff AI scheduler |
| Lost & found | Post item + contact | Image matching AI |
| Fee tracker | Manual add + due list | Full accounting suite |

---

## 5. Common Mistakes

1. MVP with 20 must-haves.  
2. MVP nobody can access (no link, no users).  
3. Building in secret for months without a try-out.  
4. Calling a slide deck the final product (research help is fine; ship path still needed).
